# DC-002 — provider answers and user events were applied without checking they answered the open question

- **Found by:** independent security/adversarial review of the engine (finding F1, high; F3 low).
- **Severity:** high (a held or new write could be replaced by another while its requests were still in flight; a
  late answer for the earlier write then advanced the later one, so the published bytes could mix two decisions).
- **Manifestations:** `sync.reapply` / a second submission during an in-flight write; late blob answers from an
  earlier catalog listing applied to a newer one; `sync.discard` during a write reported "nothing was written";
  `connect.submit` while connected; a new investigation id colliding with an existing directory.
- **Root cause:** correlation ids mapped to the *kind* of question (`Op`), not to the *instance* that asked it, and
  event handlers did not check the state they were legal in.
- **Class-level fix:** every write carries a `Generation`; each request is recorded with the generation that asked it
  and an answer is applied only while that exact write is still in flight (`Shell.emitGen`, `Shell.onEffect`). Blob
  reads are content-addressed (`OpBlob(id, file, sha)`), applied only to an entry still listing that blob. A write
  starts only from `Idle`/`Held`; reapply only from `Idle`; discard only from `Held`; connect only from
  `Disconnected`/`Refused`; a new investigation id must not exist in the catalog. A change waiting to be re-applied
  is never dropped: if the reload fails or the target becomes unreadable it returns to a visible hold.
- **Proof:** tests `15`, `15b`, `15c` (EngineTests.fs); the 30 earlier flow tests unchanged and green.

## Closure review (evidence/quality/closure-review-DC-002-004.md)

An independent reviewer found the class still open after 3cd37f3 and confirmed three variants by running them:
P2 (high) a re-apply whose target is refused at listing never resolved and hid the held change; P3 (medium) a late
blob answer during the reload started the re-apply from the pre-reload state, and two refreshes could overlap;
P5 (low) reconciliation reused the held attempt's generation. Fixed together: a re-apply target that is
Invalid/Unreadable at listing returns to a visible hold; a re-apply starts only after its reload completes and
`refresh` refuses while one runs; reconciliation (and renewal into it) takes a fresh generation. Test 15 now sends
the real `refresh` event. Regression tests `20b`, `20c`, `20e` fail on the earlier engine and pass now.

## Second closure review (evidence/quality/closure-review-2.md)

Variant A (medium): a credential renewal could start a write while a reload was running; the reload's late answers,
accepted after the save verified, replaced the head and catalog with the pre-write listing. Fixed at the class:
`startWrite` itself refuses while a reload runs, so no entry point can start one; the view offers retry, renew,
re-apply and reconcile only when they would be accepted (residual B). Test `22` fails on the earlier engine.
