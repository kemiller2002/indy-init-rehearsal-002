# DC-003 — failures after the ref update was sent were reported as definite

- **Found by:** independent security/adversarial review (finding F2, medium; F4 low).
- **Severity:** medium (the user was told "not saved" and offered Retry for a change that may already be on GitHub;
  retrying then raced the applied write).
- **Root cause:** failure classification ignored the write stage. Once `PATCH /git/refs` has been sent, a network
  error, a cancelled request or a read-back mismatch cannot prove the branch did not move.
- **Class-level fix:** `Shell.onWrite` classifies failures by stage: at or after `UpdatingRef` every failure is
  `Unknown` (reconcile only, no Retry); a cancelled request is `OutcomeUnknown`, not `Offline`; a read-back that does
  not match is `Unknown`. Reconciliation never sends a PATCH with an empty sha: if no commit was created it publishes
  again from the blobs.
- **Proof:** tests `11c` (updated expectation), `16`.

Related lows fixed in the same change: F5 (blob size cap 4 MiB → `R002.FILE_TOO_LARGE`; duplicate directory names
refused; truncation surfaced), F6 (repository identity `full_name` must equal the requested owner/repo — test `17`),
F7 (site build starts from a clean WASM output, ships no PDBs), F8 (permanently mounted polite and assertive live
regions; critical news is assertive), F9 (`auth.renew` replaces a refused credential in memory and republishes the
held change — test `18`).

## Closure review (evidence/quality/closure-review-DC-002-004.md)

completed, after the branch moved, threw `KeyNotFoundException` inside `Shell.handle` (the rebase path built a tree
from missing blob shas). The rebase now restarts at blob creation when any blob sha is missing. Lows fixed with it:
an Unknown hold accepts a renewed credential and reconciles with it; a network failure after a commit was created is
no longer described as "nothing was sent"; a rate-limited 403 (P4, filed under DC-004) is a retryable hold.
Regression tests `20` and `20d` fail on the earlier engine and pass now.

## Atomic GraphQL save (DC-005, closure review 6)

The publication is now one request, so "after the update is sent" begins with that request: any failure answering it
that is not a refusal GitHub stated (a GraphQL error, or an HTTP status below 500) is outcome-unknown — a network
failure included, because it may come after GitHub received the request. Reconciling resends only while the branch
still names the base, under the same guard, so a resend can never apply twice. Test `22c` (pre-rebase commit) is
replaced: with no client-side commit, there is nothing stale to resend; `20` now covers reconciling an unsent save
after the branch moved, `10` an offline save, `22e` a 5xx answer.

## Seventh closure review (evidence/quality/closure-review-7.md)

The atomic save closed DC-005's safety question, but the write forgot that an earlier send might have landed: a
failure while reconciling was reported "not sent" (F1), an applied save followed by another writer's change was
reported "not written" (F2), stale reads turned an applied save into "kept moving" (F4), and an untyped GraphQL error
counted as a refusal (F3). One fix covers the class:

- **`MayHaveApplied`** on the write, set whenever a send's outcome is unknown (and on every Unknown hold). While it is
  set, every failure is outcome-unknown, never NotSent, WriteFailed or "kept moving".
- **Recognition by command id.** A correlation id names exactly one command group (CONTRACT §5.4). When a moved head
  holds a changed investigation, the engine reads its `events.ndjson` and looks for this command's id: found → saved
  (reported plainly, catalog re-read); absent → a conflict that says the change is not on the branch.
- **Only stated refusals refuse.** `STALE_DATA`, `FORBIDDEN`, `RATE_LIMITED`, `NOT_FOUND`, `UNPROCESSABLE`; any other
  GraphQL error is reconciled as unknown, and an answer naming the created commit is applied whatever else it reports (F7).
- **A fresh bound per confirmation** the user asks for (F5).

Tests `26`–`26f` fail on eb7e12e and pass now. Residual F6 (low): if someone removes our applied save (a force-reset
to exactly our base, or a revert of this investigation to its base state) before we reconcile, the reconcile publishes
it again; only our own change is re-added, and no other writer's commit is touched.
