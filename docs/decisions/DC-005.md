# DC-005 — reads of mutable state could be answered from the browser's HTTP cache

- **Found by:** live acceptance run 39977289458 (real GitHub, build d031dd6). After a verified write and a reload,
  reconnecting showed the branch head from *before* the write (8ba1c78) and no investigation.
- **Severity:** high (a user could see stale data for up to a minute after their own or another writer's change,
  and decide commands against it; DC-001's base-commit parenting prevents an overwrite, but the view is wrong).
- **Root cause:** GitHub's REST API answers with `Cache-Control: private, max-age=60`. The browser cache may serve a
  later `GET /git/ref/...` or `GET /repos/...` from that copy. Limen's Http effect has no cache-mode field, and
  GitHub's CORS policy does not allow a `Cache-Control` request header.
- **Class-level fix:** an `ApiRequest` declares whether it reads mutable state (`Fresh`). Ref and repository reads
  are fresh and are sent under a unique URL (`?fresh=<correlation id>`), so no cache can answer them.
  Content-addressed reads (commits, trees, blobs by SHA) keep stable URLs: caching them is correct.
- **Proof:** test `21` (every ref/repository read has a unique URL; addressed reads do not); live L4b re-run.

## Second live finding (run 39980845597, build bd636f3): the nonce was not unique across sessions

Recorded evidence: the page's ref read after the reload went out as `?fresh=gh-2`, was not served by the browser
cache, and GitHub answered the pre-write head (8776d43) with `Cache-Control: private, max-age=60, s-maxage=60`
while an independent read at the same moment answered the written commit (be5adde). Correlation ids restart at
`gh-1` with every page load, so the first session's connect had used the identical URL, and GitHub's shared cache
answered it. The nonce is now derived from the per-message random seed (`Ids.derive Context.Seed`), unique across
sessions. Test `21` now also connects a second engine (a reload) and requires disjoint fresh URLs; it fails on the
previous engine and passes now.

## Second closure review: the read after the PATCH (residual C)

The verify step carried on whatever the ref read said. It now decides by ancestry (`compare ours...ref`): the
branch naming our commit, or a descendant of it, verifies; a ref behind our commit is a stale replica (GitHub
accepted the non-forced PATCH, so the commit read-back decides); a diverged branch is outcome-unknown. Test `22b`.
Known residual: a force-reset of the branch to exactly our parent, immediately after our PATCH, is
indistinguishable from a stale replica by any single read; the next write or refresh then shows the true state.

## Third closure review: reloads answered by a lagging replica (evidence/quality/closure-review-3.md)

The verify step allowed for lagging replicas, but the reload path did not: a reload whose ref read named an older
commit replaced the head and catalog, moving the view back past a save it had just verified (also on the automatic
reload after a rebased save). A reload now never moves the view back in history: when its ref read differs from the
catalog's read point it asks `compare head...ref`; a ref behind the shown head is a lagging replica and the newer
state is kept (with a notice); a newer or rewritten branch is shown. Test `23` fails on the earlier engine.
A renewal refused during a reload no longer swaps the credential; the typed token stays in the form (test `23b`).

## Fourth closure review (evidence/quality/closure-review-4.md): anchor, re-read, adopt

Keeping the newer state on an older answer was anchored on the read point (not the last verified save), so moved and
rebased saves still rolled back (Q1, Q2b); and it kept the newer state forever, so a deliberate rollback by someone
else was never shown and the next save re-published what they removed (Q3). Now: a reload compares the ref read
against the newest commit this session knows is on the branch (its last verified save, else the read point); an
older answer is re-read once under a fresh URL, and if the second read still names it, it is adopted with a notice
(the branch was reset; never build on a state GitHub no longer holds). A compare GitHub cannot answer (404/422, no
common history) adopts the ref (Q4). Tests `24`, `24b`, `24c`, `24d` fail on the earlier engine.

## Fifth closure review (evidence/quality/closure-review-5.md): the class-level fix

Each earlier round fixed the reload's display logic case by case. The remaining variants (R1: the anchor did not
follow heads adopted from other writers; R3/R4: two stale answers, or a stale answer after a real reset, could make the
view build on a commit GitHub no longer names) share one root cause: publishing safety depended on what the view
showed. Two changes close the class:

- **A monotonic anchor.** `Live.Known` is the newest commit the session has confirmed on the branch (every adopted
  reload, every verified save); reloads compare against it.
- **A base check before every publication.** Right before the non-forced ref update, the engine re-reads the branch
  under a fresh URL. If it does not name the commit the change was built on, the change takes the existing
  reload-and-rebase path (or becomes a visible conflict) instead of being published. A non-forced update can
  fast-forward from an older, reset head; with the check, no sequence of stale reads can re-publish removed commits.

R2: only "no common history" (404, 422) adopts the ref on a failed compare; any other failure keeps the state and
reports. Tests `25`, `25b`, `25c` fail on the earlier engine. What remains is display-only: two consecutive stale
answers can show an older view until the next reload; nothing is written on it.

## Sixth closure review (evidence/quality/closure-review-6.md): REST cannot compare-and-swap

The base check narrowed the window but could not close it. A ref read can itself be answered by a lagging replica
(V1: the check reads the stale base and passes), and the branch can move between the check and the update (V2: a
reset in that gap is fast-forwarded over). Both end the same way: a non-forced REST ref update re-publishes onto a head
GitHub no longer names. REST has no conditional ref update, so no sequence of REST reads makes it safe.

**Fix (owner decision: atomic GraphQL save).** The REST write sequence (blobs → tree → commit → base check → PATCH) is
replaced by one GraphQL `createCommitOnBranch` request with `expectedHeadOid` = the commit the decision was made on.
GitHub creates the commit and moves the branch in one step, and refuses with `STALE_DATA` (nothing applied) unless the
branch still names that commit. The guard is evaluated by GitHub at the moment of the write, so no stale read and no
race can make it apply over a newer or reset head.

- **Refused (`STALE_DATA`)** → the existing reload-and-rebase path: rebuild on what the branch names now only if this
  investigation is unchanged there, else a visible conflict. A rebuilt save is guarded by the new head. A reload that
  is itself answered by a lagging replica rebuilds on the stale commit, and GitHub refuses that too (test `22b`).
- **Reset between read and save** → refused, then rebuilt on the commit the branch names after the reset (test `22c`).
- **Unknown outcome** (timeout, cancellation, network failure, 5xx) → never "not written" (DC-003). Reading the ref:
  still the base → resend under the same guard, bounded by `maxRebases` (test `22d`); otherwise reload that head and
  recognise the change by its blob ids, or treat it as moved (tests `11`, `11d`, `22e`).
- **Verification** reads back the commit GitHub returned (commit, tree, byte-equal blobs, re-validation); no ref read
  is needed to find it, so the earlier "stale verify-ref read" and its residual (a force-reset to exactly our parent
  right after the PATCH) no longer exist.

The base check (fifth review) is removed: the guard subsumes it, and its stale-read false conflicts (D3) go with it.
Tests `22b` (V1) and `22c` (V2) cannot run against the REST engine, which never sends a guarded request; closure
review 6 recorded the REST failures. Live acceptance must confirm that GitHub's GraphQL API accepts the save from the
browser with the run's token.
