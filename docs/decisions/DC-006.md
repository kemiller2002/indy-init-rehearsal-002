# DC-006 — a framework file failing mid-boot left the page loading until the 90 s timeout

- **Found by:** deployed acceptance on main 3eb7995 (run 39983316689). Right after the Pages deploy, the CDN
  answered 503 for one framework file (`System.ComponentModel.EventBasedAsync…wasm`); its body failed the
  integrity check and the .NET loader rejected internally.
- **Severity:** medium (no data at risk, but a user saw a spinner for up to 90 s instead of the recoverable failure;
  violates WASM-LOAD-005's prompt failure and recovery).
- **Root cause:** the loader downloads framework files in parallel and reports a failed one only as an unhandled
  rejection; the kernel's start promise never settles, so only the timeout ended the wait.
- **Fix:** while starting, any unhandled rejection ends the start immediately with the recoverable failure and a
  focused Retry (`src/kernel/main.js`). Browser test "a 503 on one framework .wasm shows the recoverable failure;
  Retry reloads to ready" (fails on the earlier kernel: no state within 90 s).
- **Not fixed here:** the CDN serving a 503 during deploy propagation is GitHub Pages behaviour. Deployed acceptance
  will be re-run on the next deployment.

## Third closure review: the first fix failed recoverable starts (evidence/quality/closure-review-3.md)

The loader retries a failed download on its own; each failed attempt is an unhandled rejection. The first fix failed
the start on the first one, before the retry, so a temporary 503 (the very CDN-propagation case above) became a hard
failure where the earlier page had recovered. Now a rejection arms a 10 s grace period, re-armed by each further
rejection; a successful retry lets the start finish, a final failure ends it with Retry well before the 90 s timeout.
Each rejection reason is logged with `console.warn` instead of being suppressed silently. Browser tests: "a single
503 ... reaches ready" (fails on the first fix) and "a 503 on one framework .wasm shows the recoverable failure".

## Fourth closure review: grace measured against download progress (B1)

The grace period counted from the last failed attempt, not from loader progress, so on a slow connection a retry
still under way failed the start. Downloads are now counted while starting; the grace period expires only when none
is in flight (the overall 90 s timeout still bounds a hung download). Browser test "a single 503 while a slow
download is still in progress still reaches ready" fails on the earlier kernel. Not changed (low): after a failure the
engine may finish starting behind the failure screen; Retry reloads the page, so nothing from it is used.
